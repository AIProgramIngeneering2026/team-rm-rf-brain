# Правила проекта Clip Forge и Definition of Done 

## 1. Модель ветвления (Git Workflow)
* **`main`** — защищённая основная ветка. Прямые коммиты (`git push origin main`) запрещены. Вся работа ведётся исключительно через Pull Request (PR).
* **Создание веток:** любая задача (Issue) выполняется в отдельной ветке, созданной от актуального `main`.
* **Формат именования веток:** `<тип>/<номер-issue>-<краткое-описание>` (на английском языке в `kebab-case`):
  * `feat/<id>-<desc>` — новая функциональность и сценарии (например, `feat/5-chat-spike-tool`)
  * `fix/<id>-<desc>` — исправление багов (например, `fix/14-empty-chat-handling`)
  * `docs/<id>-<desc>` — документация, требования, контракты, ADR (например, `docs/2-requirements`)
  * `test/<id>-<desc>` — добавление или доработка автотестов (например, `test/9-job-transitions`)

## 2. Правила написания коммитов (Conventional Commits)
Каждый коммит должен быть атомарным и оформляться по стандарту **Conventional Commits**:
`<тип>(<область>): <краткое описание в повелительном наклонении>`
`docs(contributing): добавить правила работы с ветками, коммитами и DoD`
* **Примеры хороших коммитов:**
  * `docs(requirements): добавить 5 сценариев с критериями приёмки и раздел «Что предложил ИИ»`
  * `feat(domain): реализовать машину состояний VodClipJob и проверку переходов`
  * `feat(tools): реализовать ChatSpikeDetectorTool для поиска пиков смеха в чате`
  * `test(domain): добавить негативные тесты на недопустимые переходы статусов VodClipJob`
  * `fix(adapter): обрабатывать отрицательные таймкоды и битый JSON от внешнего сервиса`
  * `chore(config): добавить .gitignore и шаблон переменных окружения .env.example`
* **Запрещено:** бессмысленные сообщения вроде `fix`, `update`, `wip`, `123`, `поправил`.

## 3. Правила Pull Request (PR) и Code Review
* **Привязка к задаче:** в описании каждого PR обязательно указывается связанный Issue из Backlog (например, `Closes #4`).
* **Атомарность:** один PR решает одну задачу из Backlog.
* **Кто делает review:**
  * Для влития PR в `main` требуется минимум **1 одобрение (Approve)** от другого участника команды.
  * Автор PR не может апрувить собственный код.
* **Как делается review (критерии качества):**
  * Формальные отписки вроде `LGTM`, `OK`, `TEST`, `+` **запрещены**.
  * **Для документов:** проверьте понятность текста, полноту критериев приёмки и учёт ошибочных случаев.
  * Начиная с Практики 3 ревьюер проверяет, что доменное ядро (`domain/`) не зависит от фреймворков, БД и `pandas`.

## 4. Стандарты разработки и безопасности
* **Язык и стиль:** Python 3.12, обязательная аннотация типов (`type hints`) для всех функций и методов, проверка стиля через `ruff`.
* **Безопасность:** коммитить реальные файлы `.env`, пароли, ключи API и дампы БД строго запрещено. Все переменные окружения описываются только в шаблоне `.env.example`.

## 5. Definition of Done (Критерии готовности задачи)
Задача (Issue) считается выполненной и готовой к влитию в `main`, только если соблюдены **все** пункты:
1. **Выполнены критерии приёмки:** реализация или документ полностью покрывают требования и сценарии (`Дано / Когда / Тогда`), описанные в Issue.
2. **Соблюдена архитектура:** код соответствует схеме `Job → Dispatcher → Registry → Tool → ToolResult` без нарушения границ слоёв.
3. **Написаны тесты (начиная с Практики 3):** добавлены позитивные и негативные автотесты на новый функционал; все тесты (`pytest`) и линтер (`ruff`) проходят локально и в CI.
4. **Обновлена документация:** при изменении логики, контрактов API или настроек обновлены `README.md`, `docs/`, `openapi.yaml` или `.env.example`.
5. **Пройдено содержательное Code Review:** получено одобрение (Approve) от сокомандника после разбора вопросов/замечаний по существу, все треды обсуждений закрыты.
